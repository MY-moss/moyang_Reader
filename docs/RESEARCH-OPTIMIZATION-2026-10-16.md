## 结论与优先级

现有 React / Tauri / Rust / SQLite 架构仍适合当前产品。优先改善大库操作、草稿保护和闲置时的重复工作；较大规模的数据库改造应由容量与延迟测试驱动。

| 优先级     | 工作                                     | 用户收益                                           | 工作量判断             |
| ---------- | ---------------------------------------- | -------------------------------------------------- | ---------------------- |
| 第一批     | 阅读库索引差量更新、耗时原生命令后台执行 | 文件多时操作更顺畅，收藏和元数据变化少做无关工作   | 中                     |
| 第一批     | 阅读草稿异步分条存储、长文撤销字节预算   | 多篇未保存文档和长文更可靠，减少内存及同步写入负担 | 中；恢复兼容要求高     |
| 第一批     | 性能基线、纯逻辑测试环境拆分             | 能量化优化效果，缩短开发反馈                       | 小到中                 |
| 第二批     | AI 按变化刷新、数据库维护移出请求路径    | 降低闲置唤醒和重复查询，避免首个请求承担备份工作   | 中                     |
| 第二批     | 存储管理页、应用与模型分开更新           | 用户看得懂空间去向，更新和清理更可控               | 中；与当前更新任务协调 |
| 按规模推进 | 技能资源去重、流式备份、向量二进制存储   | 降低长期积累后的空间和导出内存成本                 | 中到大；需要迁移与回滚 |
| 后续功能   | PDF 选字批注、来源批量核对、知识健康检查 | 提升阅读与知识积累的实际用途                       | 分别作为独立任务       |

“第一批”是建议，不表示已经实施或已经测出界面提速。

## 代码与运行效率的具体机会

### 1. 索引失效范围和后台任务边界

代码依据：`src/application/useBookroom.ts:95`、`src-tauri/src/commands/bookroom.rs:183`、`src-tauri/src/commands/search.rs:825`。

多格式索引 effect 依赖 `workspaceFiles`、`workspaceIndex` 和通用 `revision`，每轮逐文件发起 `fileMetadata`。收藏、摘录、保存视图等动作也调用同一个 `refresh()`；因此即使正文没有变化，也会重新进入文件元数据核对。现有差量逻辑避免了无变化正文的重新解析，但没有消除这些逐文件调用。

`bookroom_request`、`search_workspace` 是普通同步 Tauri 命令，内部包含数据库查询、目录/文件操作。根据 [Tauri 2 官方文档](https://v2.tauri.app/develop/calling-rust/#async-commands)，没有异步标记的命令在主线程执行。这里可确认执行路径存在阻塞风险；尚未录制当前应用的桌面卡顿轨迹。

建议：分开正文索引和收藏等元数据的失效标记；watcher 合并出的变化路径直接驱动有界队列；冷启动才做完整核对。耗时命令采用已有 AI 桥接使用的阻塞线程模式，保留原有授权和保存串行语义。批量元数据查询可以减少大量跨进程往返；不要无限并行读取磁盘。

验收场景：1 万文件阅读库中新增一条收藏，不触发逐文件重新核对；单文件变化只更新对应正文索引；冷索引时窗口仍可拖动、切换和取消，旧结果不能覆盖新任务。记录调用次数、首批结果时间和 UI 长任务。

### 2. 阅读草稿存储与大文档撤销

代码依据：`src/features/recovery/draft-recovery.ts:3`、`src/features/editor/editor-history.ts:1`、`src/application/useEditing.tsx:393`。

阅读草稿仍将全部快照同步序列化后写入 localStorage，最多 8 篇，预算 3,000,000 个估算字节，单篇草稿上限 100 万字符。快照同时保留原文和草稿：两个约 80 万字符的版本仅字符串估算就约 320 万字节，因此可能先触发总体预算。失败和淘汰已有提示，不能把它表述为没有保护或必然静默丢失。

建议：桌面草稿分条存入阅读域的原生存储；浏览器预览使用 IndexedDB。保存确认、关闭窗口前的 flush、旧草稿导入和冲突原文必须统一定义。初期保持完整快照以降低恢复复杂度，再评估差量存储。

撤销栈目前保留 100 个全文字符串，没有按字节的上限。对于每版约 100 万字符的内容，100 版在逻辑上就是约 1 亿字符；按 UTF-16 粗估约 200 MB，但实际堆内存受引擎字符串共享影响，尚未测量。文档缓存的 64 MiB 限额不覆盖撤销栈和所有打开会话。

建议先增加每会话及全局历史预算、连续输入分组，再评估差量操作。不能直接把不同编辑器的历史各自保留，否则会破坏同一文件在双窗格与编辑模式之间共享撤销的约定。[CodeMirror 的事务与变化集](https://codemirror.net/docs/guide/)可以作为实现参考。

验收场景：20 篇未保存文档、百万字符长文、中文组词、异常退出、断电恢复、保存失败和双窗格切换；记录内存峰值和恢复结果。超出容量必须明确告知，不自动抹去未落盘内容。

### 3. 长文渲染和根状态更新

代码依据：`src/features/documents/rendering/markdown.ts:112`、`src/features/reader/components/ProgressiveReaderContent.tsx`、`src/application/useDocumentSessions.ts`。

Markdown 仍完整解析正文；长文分块改善布局和绘制，未消除全文解析，也不是只挂载可见块的虚拟列表。会话订阅返回整个会话集合，每次内容变更会通知应用编排层。

建议先对 20 万/100 万字符、表格、公式、双窗格做录制，再选择 Worker 解析、丢弃旧解析结果、会话级订阅或稳定组件边界。不要全面堆叠 memo，也不要在无测量时重写状态架构。虚拟化必须保留目录定位、页内搜索、选区、嵌入和打印。

### 4. AI 闲置工作与数据库维护

代码依据：`src/features/ai/useAiSpace.ts:139`、`src-tauri/src/ai.rs:10`、`crates/ai-core/src/runtime.rs:86`、`crates/ai-core/src/migration.rs:5`。

AI 激活时每 12 秒刷新；刷新会请求统计和词法检索，有查询且启用语义时再请求混合检索。`stats` 成功后也会触发后台索引维护。桌面每个请求重新打开 Store，打开过程检查快照轮换；进入新的日/周周期时，某个请求会承担 `VACUUM INTO` 完整快照成本。不是每次请求都做完整备份。

建议：复用适量连接，将统计刷新与结果刷新分开，数据没有变化时不重复检索；隐藏/最小化时降低轮询；维护任务单独调度并显示状态。保留跨 MCP 进程变化发现和过期记忆按时间失效，不能只监听当前 UI 的保存事件。

若采用 SQLite `PRAGMA data_version`，必须在同一条长期连接上比较，并单独处理该连接自己的写入；不同连接的值不能直接对比，见 [SQLite 官方说明](https://www.sqlite.org/pragma.html#pragma_data_version)。

验收：30 分钟无操作和跨进程连续写入两种场景，比较请求次数、后台线程启动次数、CPU/写入量以及内容可见延迟。过期内容和恢复焦点后的数据必须及时更新。

## 存储结构的后续优化

### 5. 技能资源按内容去重，备份按流输出

代码依据：`crates/ai-core/src/store.rs:316`、`crates/ai-core/src/exchange.rs:6`、`src/features/ai/transfers.ts:196`。

每次保存将完整 Record JSON 写入当前记录及新的历史版本，技能资源内容包含在 JSON 内。历史和资源接口按需读取已降低返回量，但存储层仍会重复保存未变化的附件。当前 JSON 备份会先在 Rust 收集全部记录和历史，再跨桥接返回给前端，前端再次序列化和编码；大备份会同时占用多份内存。

建议：先将附件改为按哈希去重的不可变资源表，记录和版本只持有引用。优先同库事务，暂不增加独立对象文件系统的恢复复杂度。迁移时保留旧版读取、指纹、版本、导入导出兼容，资源回收必须检查所有历史引用。

桌面备份可以在用户选定路径后由原生层分批写入临时文件，完整校验后原子发布，返回进度和简洁回执；旧版 JSON 导入继续兼容。数据库快照可评估 [SQLite Online Backup API](https://www.sqlite.org/backup.html) 的分页复制能力，它不是“只保存变更”的增量备份格式。现有 7 日/4 周保留策略本身已经有界，不必删除恢复能力换空间。

验收：同一份 10 MB 技能资源连续编辑正文 100 次，资源实体只增加一份；历史恢复字节一致。大备份峰值内存不随全部历史等比例多份增长，取消或磁盘不足不公布不完整备份。

### 6. 向量格式与大规模搜索

代码依据：`crates/ai-core/src/store.rs:37`、`crates/ai-core/src/semantic.rs:307`。

当前向量保存为 JSON 文本，搜索在范围过滤后逐条反序列化为 `Vec<f64>` 并计算余弦。范围过滤和最后返回 100 条候选，并没有消除对该范围内全部向量的扫描。复杂度随分块数量和维数增长，但当前默认个人库仅 26 条向量。

建议顺序：建立 1 千/1 万/5 万分块数据集 → 拆分查询嵌入、SQL、解码、相似度计算耗时 → 评估版本化 Float32 BLOB、预归一化和有界缓存 → 确认大库仍不满足延迟预算后，再比较专用向量索引。不能先用关键词筛出少量候选而牺牲原本应由纯语义找到的内容。

验收：除延迟和体积外，复跑现有 80 条检索样本，补足真实中文长资料和困难反例；检查 Recall@5、无答案误报、范围隔离、模型版本变更、取消和并发更新。现有 80 条样本结果是项目回归证据，不代表通用检索准确率。

### 7. 存储管理与交付成本

代码依据：`scripts/portable-package.mjs:48`、`scripts/clean-workspace.ps1`、`WORKSPACE.md`。

当前完整便携包复制本地模型及运行程序，适合离线交付，但多个版本会重复占用这部分空间。当前更新任务已要求“不重复下载模型”，建议直接在该任务落实：完整离线包继续保留，日常更新只带应用和 MCP，模型按版本单独管理，保留可校验的旧版本回退。

产品可新增“存储与维护”页，区分原文件、草稿、历史、索引、快照、模型和可重建缓存；显示容量、保留规则、预期释放量和最近恢复验证。开发缓存另列开发文档。现有清理脚本有路径和链接检查，不应改成一键递归清空全部应用目录。

SQLite 删除数据后不一定缩小文件，整理只能按空闲比例、空间余量和维护窗口进行；[VACUUM 官方文档](https://www.sqlite.org/lang_vacuum.html)说明其空间与锁定成本。当前库仅 2 个空闲页，无需立刻整理。

## 代码维护与开发效率

本次全量前端测试 83 个文件、284 项通过，总耗时 93.50 秒。测试主体累计 3.90 秒，环境初始化累计 281.45 秒；后者跨 worker 累计，不能直接当作墙钟耗时。配置对所有测试使用 jsdom，纯算法测试也承担浏览器模拟成本。

对相同 5 个文件、16 项测试按顺序做了一次比较：

| 环境              | 结果  | Vitest 报告总耗时 | 环境初始化累计 |
| ----------------- | ----- | ----------------: | -------------: |
| 当前 jsdom        | 16/16 |           3.84 秒 |        8.66 秒 |
| 命令行覆盖为 node | 16/16 |          0.748 秒 |         1 毫秒 |

样本为 editor-history、document-cache、reading-position、workspace-tree、pane-layout。单次顺序运行有缓存和机器负载因素，不能宣称全套能提速五倍。下一步按 [Vitest 环境配置](https://vitest.dev/guide/environment.html)拆分纯逻辑与 DOM/React 用例，再复测全套。React `act(...)` 环境告警也应修正测试配置和异步等待，不能屏蔽日志代替处理。

较大的实现文件有 export.ts（981 行）、search.rs（911 行）、MarkdownWysiwygEditor.tsx（878 行）、useDocumentSession.tsx（712 行）。行数只作为审阅入口；按导出格式、搜索缓存/持久化、编辑器生命周期等职责拆分，同时补齐跨层契约和错误类型，比单纯把代码移动到更多 hook 更有价值。

架构门禁已检查依赖方向和 App.tsx 大小，可继续增加“业务 UI 不直接调用原生 invoke”、关键状态只创建一次等可机械检查的规则。性能基线应覆盖冷启动、首文档、长文输入、1 万文件单次变更、闲置、备份内存和磁盘增长；所有阈值先由相同设备的重复测量确定。

## 值得继续开发的用户功能

1. **PDF 阅读闭环**：当前 PdfPreview 主要是 canvas、翻页和缩放。优先增加文字选择、复制、搜索高亮和选区摘录，再做批注定位；扫描件 OCR 作为独立可选能力，有明确模型大小和处理进度。可复用 [PDF.js 的显示层和查看器能力](https://mozilla.github.io/pdf.js/getting_started/)。
2. **来源批量核对**：已有单条来源检查与快照比较，可增加批量检测、变化列表、逐项采纳和失效定位修复；保留导入快照与个人修改，不能自动覆盖。
3. **知识健康检查**：基于已有过期、冲突、合并和活动记录，提供重复候选、无来源内容、长期未用记录的集中核对；先解释和预览，再由用户决定更正、合并或归档。
4. **数据恢复演练与诊断导出**：从已有快照恢复到隔离目录，核对记录、资源、历史和权限；诊断默认仅含计数、耗时和版本，不含正文或 API 密钥。

应用内聊天、多模型 API、导航简化和在线更新已有进行中的任务，不重复开另一套实现。Canvas、通用脚本查询和跨设备同步可以继续研究，但会增加数据模型、冲突处理和维护成本，建议排在上述基础能力之后。
