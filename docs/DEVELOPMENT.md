# 开发流程与工程指南

## 环境与启动

在本目录工作，使用支持当前 Vite 版本的 Node.js（建议与本次验证环境保持一致，见验证报告）。先 `npm ci`，锁文件变化需要说明原因。前端 `npm run dev`，桌面 `npm run desktop`，生产前端 `npm run build`，预览产物 `npm run preview`。

Windows 桌面要求 Rust MSVC 工具链、C++ Build Tools、Windows SDK 和 WebView2。可先运行 `node --version`、`npm --version`、`cargo --version`，再用 `npm run rust -- check --manifest-path src-tauri/Cargo.toml` 检查原生工程。首次编译会下载依赖，耗时明显高于前端启动。

保留原有启动脚本，包括后台启动开发服务器、共享 Cargo 缓存与 Windows 窗口隐藏。开发服务仍使用 1420。浏览器测试使用 4173；测试前必须重新构建，不能把旧产物结果当作新代码通过。

## 日常工作步骤

### 确定一个可验收场景

写清触发条件、预期行为、保存的数据、失败处理。例如“外部工具修改当前文件后，未保存编辑不能被覆盖”。查看功能矩阵、对应 hook、桥接函数、原生命令和已有用例。不得以“优化体验”作为唯一验收条件。

### 选择职责和实现顺序

纯算法放在 feature 模块，磁盘/系统能力通过 platform bridge 和原生命令，React 状态协调放 application，视觉排版放组件和 styles。先定义类型契约，再实现最小垂直切片。新组件不能直接依赖根应用状态；给它所需的最小 props。

### 实现与检查

1. 修改业务规则，运行最相关测试。
2. 修改编排时检查旧/新文档切换、异步请求淘汰、清理函数、Blob URL 和监听退订。
3. 修改界面时检查空、加载、错误、禁用、有修改和长文本状态。
4. 运行 `npm run check`，包含架构检查、lint、单元测试、构建。
5. 交互变化运行 `npm run test:e2e`；原生变化运行 Rust 测试。
6. 将实测结果写入变更说明；未执行的检查标记为未执行。

### 评审与交付

评审内容包括：用户可感知变化、数据兼容性、权限范围、错误处理、验证证据和回滚方案。确认没有仓库外实现导入、没有提交依赖/构建缓存、没有改动无关用户文件。更新功能矩阵、使用指南和相关架构决策。

## 迭代任务模板

AI 内核与协议测试：`npm run test:ai`。独立 MCP 构建：`npm run build:mcp`。正常 `npm run desktop` 与 `npm run tauri -- build --no-bundle` 会自动构建对应配置的 MCP 程序。优化版桌面程序与 MCP 位于共享 Cargo target 的 release 目录；便携交付时两者放在同一文件夹。AI 存储及接口修改流程见 [AI 架构](AI-ARCHITECTURE.md)。

```markdown
目标：用户在什么条件下完成什么操作。
范围：要改的模块与保持的接口。
依赖：前置类型、数据或任务。
验收：正常路径、失败路径、持久化结果。
验证：具体命令及人工检查。
风险：文件写入、兼容性、权限与异步竞态。
回滚：恢复哪些代码/配置，是否影响用户文件。
证据：实际结果、截图或日志位置。
```

每个任务以 1–5 个相关文件为理想范围；跨层任务按一条完整用户路径拆分。可以并行评审文档或互不依赖的功能；涉及共享状态和 IPC 契约的任务先确定接口，避免同时改同一控制流。

## 完成定义

功能符合验收；不丢失用户数据；类型、构建、静态规则与相关回归通过；浅深色和紧凑窗口可用；文档与实现一致；留下明确的验证记录。速度或视觉改善要用实测支持，不能仅凭模块数量宣称性能提升。

## 发布流程

本次是可运行重构开发版，正式发布流程单独执行：确定产品版本和更新渠道 → 检查安装标识与文件关联策略 → 配置签名和发布密钥 → 构建 Windows x64 安装包 → 干净环境安装/卸载 → 单实例/拖放/关联/重启恢复 → 更新验证 → 人工确认发布。

仓库根目录是唯一工程入口。`.github/workflows/quality.yml` 统一执行前端、脚本、Rust、浏览器与真实桌面检查，合并门禁名为 `Quality checks`。旧工程的镜像发布、独立检查与重复配置已经移除；不使用旧版自动更新渠道。目录清理与旧源码恢复见 [目录维护](../WORKSPACE.md)。

## 0.11 工作台与 AI 交付流程

本轮已确认范围与依赖顺序见 `tasks/workbench-upgrade.md`：先完成阅读器真实桌面验收，再进入 AI 数据与客户端。实现按可运行切片推进，新增交互同步场景测试；不以模拟 MCP 或配置文件存在代替真实客户端完成记录。

1. 核对文档会话/窗格边界、来源位置和数据版本，定义旧数据与异常恢复行为。
2. 改动后运行相关单元与交互测试；文档保存、迁移、冲突、检查点改动必须验证数据结果。
3. 最终运行架构、格式、lint、前端单元、Rust 内核和真实 MCP 协议测试。
4. 顺序执行桌面构建与桌面测试，然后浏览器构建与浏览器测试，不并行改写 dist。
5. 运行 `node scripts/evaluate-ai-search.mjs` 建立真实中文样本评测；`--reuse` 仅复用已经建好的索引。记录冷索引与热查询，保留失败样本。
6. 完成独立界面审阅和文档核对。真实客户端的模型服务、MCP 权限和钩子信任分别检查；未通过项目保留待办。
7. `node scripts/package-portable.mjs` 从本次成功的正常优化构建生成 `release/<版本与构建时间>/`。先写入暂存目录，完整复制、生成校验和后再公布 `release/latest.json`；失败不更改旧包，运行中的 MCP 不需要退出。如本机已准备模型，则一并打包 CPU Ollama、模型及许可证。原始测试数据库与报告不作为打包依赖，不进入包或 GitHub。该流程不发布远程渠道、不注册文件关联。
8. 对打包后的程序和 MCP 做启动、持久化与接口烟测，核对版本和校验和，再记录交付状态。

本机 Cargo 联网索引偶有停顿。锁文件和依赖已缓存时可用 `CARGO_NET_OFFLINE=true` 进行复现；不能用离线参数掩盖缺失依赖或绕过失败构建。

运行脚本回归用 `npm run test:scripts`（已纳入 `npm run check`），覆盖 Windows 开发启动和打包失败保留旧包。`node scripts/test-portable-release.mjs` 检查 latest 指向的包，也可在末尾传入包目录；校验摘要后运行真实 MCP、可选随包模型及桌面。烟测使用临时数据目录和未占用端口，不使用个人书房与设置。

显式设置 `MOYANG_DATA_DIR` 可隔离桌面设置、书房与检索缓存，AI 默认存放在其 `ai-space` 子目录；`MOYANG_AI_DATA_DIR` 的优先级更高。未设置时仍沿用已有用户数据路径。该覆盖用于测试与独立实例，不会自动迁移旧数据。

## 故障处理

- 1420 被占用：关闭占用端口的开发服务后重试。
- Rust 链接器缺失：安装 Visual Studio C++ Build Tools 与 Windows SDK，重新打开终端。
- 浏览器添加文件夹无结果：这是预览边界，使用桌面模式。
- 本地版没有自动更新入口：使用新版应用进行升级，不连接旧工程的发布渠道。
- 测试读取旧界面：先 `npm run build`，确认 4173 预览来自本目录。
- 资源被阻止：先检查相对路径是否处于用户已授权范围，不能扩大权限来掩盖路径错误。
