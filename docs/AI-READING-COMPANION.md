# Moyang Reader — AI 阅读伴侣开发路线

> 本文定义 v1.0 之后的 AI 阅读伴侣产品目标、交互约束、架构边界和可拆分切片。它不是当前 TODO 状态数据库；当前开发仍只从 [`AI-TASKS.md`](AI-TASKS.md) 选择任务。当前 v0.14 的 `DocumentAdapter / IndexProvider / AiProvider / ConsentScope` 是本路线的前置基础。

## 1. 产品目标

Moyang Reader 的 AI 方向不是“在阅读器旁边塞一个聊天框”，而是让 AI 真正理解**用户正在读什么、已经读到哪里、当前选中了什么**，并在需要时提供低打扰、可追溯、不会越权的帮助。

目标体验：

- 平时不打扰，AI 入口不抢占阅读空间；
- 选中文字后可以立刻“解释 / 为什么 / 举例 / 联系前文 / 总结 / 翻译”；
- 右侧阅读伴侣可以围绕当前文档持续问答；
- 用户走神时可以一键回答“我刚刚读了什么？”；
- 随阅读积累人物、术语、概念和关系，但默认只使用已经读过的内容，避免剧透；
- 关闭 AI 后，阅读、编辑、搜索、批注、文件安全等核心能力完全不受影响。

## 2. 不变原则

### 2.1 本地优先，AI 是可拔掉的附加层

- 原文件继续是真源，AI 不改变 Markdown / TXT / DOCX 等保存格式。
- AI 缓存、摘要、实体和 embedding 都属于派生数据，必须可删除并重建。
- 不默认联网；远程 provider 必须由用户显式配置和启用。
- API Key / token 不进入 portable settings、工作区文件、日志或仓库。

### 2.2 上下文必须可见

每次请求至少能让用户知道：

- 使用哪个 provider / model；
- 发送的是选区、当前章节、当前文档还是其他范围；
- 当前格式的文本提取质量；
- 回答依据来自哪里。

第一阶段不需要复杂“审批流”。对只读请求使用轻量、可理解的范围提示即可；涉及写回时继续使用候选结果 + diff。

### 2.3 默认不剧透

“当前文档可读”不等于“整篇内容都算用户已经读过”。后续人物卡、概念卡和关系图必须区分：

- `currentPosition`：当前阅读位置；
- `recentAnchors`：最近实际停留/阅读过的片段；
- `readCoverage`：明确记录的已读范围；
- `fullDocument`：整篇正文，仅在用户明确允许时用于总结或问答。

不能仅使用“最大滚动位置”推断前面全部已经读完；搜索跳转、目录跳转和快速定位都可能让用户跨越未读内容。

### 2.4 回答必须带来源

第一阶段不要求学术级 citation system，但每个回答至少显示来源层级：

- 选区；
- 文档名；
- 标题 / 小节；
- 必要时显示片段预览。

后续 RAG 再增加跨文档来源和定位跳转。

### 2.5 先做“爽”的垂直切片，不先做大 Agent

优先顺序：

1. 选区快捷操作；
2. 当前文档问答；
3. “我刚刚读了什么？”；
4. 人物 / 术语记忆卡；
5. 防剧透记忆地图；
6. 工作区 RAG；
7. 写作辅助和受控 Agent。

## 3. 核心交互

### 3.1 选区快捷操作

用户选中文字后出现轻量浮层，默认动作建议：

- **解释**：用更清楚的语言说明；
- **为什么**：补充原因、推理链和前提；
- **举例**：给一个贴近原文语境的例子；
- **联系前文**：只在已授权的已读上下文中找关联；
- **总结**：压缩选区；
- **翻译**：在用户设置的目标语言之间转换。

交互要求：

- 不遮住选区主体；
- Esc 关闭后焦点回到阅读区；
- 键盘可以打开和选择动作；
- 请求中可以取消；
- 失败不会清掉选区或改变文档；
- 第一阶段回答只展示，不自动写回。

### 3.2 阅读伴侣侧栏

建议复用现有右侧上下文面板的 contribution 思路，而不是另做永久占宽的新主布局。

侧栏第一阶段只做：

- 当前文档问答；
- 当前选区问答；
- 当前章节 / 当前文档总结；
- 最近几个问题的本次会话历史。

暂不做：跨工作区 Agent、自动调用外部工具、后台自主任务。

### 3.3 “我刚刚读了什么？”

这是阅读伴侣的第二个高辨识度功能。

目标不是总结整篇文档，而是总结**最近实际阅读过的内容**。建议基于最近若干 `recentAnchors` / 可见段落快照构建上下文，而不是简单截取当前位置前 N 个字符。

输出建议保持很短：

- 3–5 条刚刚发生/讲到的关键点；
- 当前最大的疑问或尚未解释的概念；
- 可选“展开回顾”。

快捷键应在命令统一后再确定，避免提前占用冲突组合。

### 3.4 人物 / 术语记忆卡

当 AI 能稳定读取已读上下文后，再提取：

- 人物；
- 地点；
- 术语；
- 观点；
- 事件。

卡片只保存派生摘要和来源定位，不修改正文。卡片必须能回答“我目前已经知道什么”，而不是“整本书真实设定是什么”。

### 3.5 防剧透记忆地图

关系图的输入只能来自 `readCoverage` 内的证据。默认不允许模型查看未读正文后再“假装不剧透”。

节点：人物 / 地点 / 概念 / 事件。

边：出现、属于、导致、反驳、认识、参与等受控关系。

每条关系保留来源片段指针，用户可跳回原文验证。

## 4. 建议的内部模型

### 4.1 ReadingContextSnapshot

建议建立一个 provider-agnostic 的只读快照，不让 UI 组件直接拼 prompt：

```ts
interface ReadingContextSnapshot {
  documentId: string;
  title: string;
  adapterId: string;
  extractionQuality: "full" | "partial" | "preview-only" | "unavailable";
  selection?: TextFragment;
  visibleSection?: TextFragment;
  recentAnchors: TextFragment[];
  readCoverage?: ReadCoverage;
}
```

`TextFragment` 至少包含：来源文档、标题/章节、文本、可恢复定位信息。

### 4.2 ReadCoverage

不要复用单一 `readingPosition` 充当“已读范围”。建议独立维护轻量覆盖信息：

- 最近实际停留的段落 / heading 范围；
- 可合并的已读区间；
- 搜索/目录瞬时跳转不自动把中间内容标成已读；
- 数据属于旁路元数据，可随工作区清理。

MVP 不需要高精度眼动式追踪；先做到“明显比最大滚动位置安全”。

### 4.3 AiRequest

业务功能只向 `AiProvider` 发送结构化请求：

```ts
interface AiRequest {
  task: string;
  instruction: string;
  context: TextFragment[];
  consentScope: ConsentScope;
  outputMode: "answer" | "summary" | "translation" | "entities" | "proposal";
}
```

具体 provider SDK、HTTP 格式、stream parsing 不进入阅读组件。

## 5. 版本路径

### 阶段 0 — v0.14：只做基础接缝

沿用现有路线：

- `DocumentAdapter / IndexProvider` 稳定文本来源；
- `CommandService / CommandContribution` 收口入口；
- `AiProvider + ConsentScope` 用 mock 验证 streaming / cancel / error；
- provider 普通配置和 secret 分离。

**退出条件：** 阅读 UI 可以调用 mock AI，但核心阅读器仍完全不依赖 AI。

### 阶段 1 — v1.1：AI 阅读伴侣 MVP

先交付两个真实可感知能力：

1. 选区快捷操作；
2. 当前文档 / 当前选区问答侧栏。

这一阶段只需要一个远程或 OpenAI-compatible provider 路径跑通，不追求 provider 数量。

### 阶段 2 — v1.1.x：最近阅读回顾

建立 `ReadingContextSnapshot + recentAnchors`，交付“我刚刚读了什么？”。

优先验证：长文档、目录跳转、全文搜索跳转、切换文档后 recent context 是否正确清理/隔离。

### 阶段 3 — v1.2：阅读记忆

先做人物/术语卡，再做关系图：

- 实体提取；
- 去重 / 合并；
- 来源跳转；
- 只基于已读范围重新计算；
- 用户可以清空派生记忆，不影响正文和批注。

### 阶段 4 — v1.2+：可选 RAG

只有当前文档问答已经稳定后再做跨工作区 RAG：

`现有词法检索 + 可选语义召回 + 合并/重排`

不让向量索引替换现有搜索，也不把 embeddings 变成不可恢复的真源。

### 阶段 5 — 更后：写作辅助 / 受控 Agent

- 改写、扩写、缩写、生成标题；
- 生成 frontmatter / 链接建议；
- 将批注整理为新 Markdown；
- Agent 只复用核心受控命令和 PermissionBroker。

所有写回继续走候选 diff，不允许静默覆盖。

## 6. 后续可拆分垂直切片

> 这些是候选切片，不要一次全部塞进 `AI-TASKS.md`。当 v1.0 完成且前置满足时，每次只提升 1–2 个到当前队列。

### RC01 — ReadingContextSnapshot 基座

- **目标**：统一获取选区、当前可见小节、最近阅读锚点和提取质量。
- **用户价值**：后续 AI 不再各自猜“当前上下文”。
- **非目标**：不联网，不做 AI UI，不做 RAG。
- **验收**：Markdown/TXT 至少完整可用；切换文档后上下文不串；目录/搜索跳转不会错误扩张已读范围。
- **建议验证**：service 单测 + 长文档 E2E。

### RC02 — 选区快捷操作 UI + mock provider

- **目标**：选区后出现“解释 / 为什么 / 举例 / 总结 / 翻译”入口，先接 mock。
- **用户价值**：先验证最关键的交互是否顺手。
- **非目标**：不接真实 API，不写回文档。
- **验收**：鼠标/键盘可用；Esc/focus 正确；取消/错误状态可理解；不遮挡主要阅读内容。
- **建议验证**：组件测试 + Playwright + a11y。

### RC03 — Provider 配置与安全密钥存储

- **目标**：跑通一个 OpenAI-compatible/远程 endpoint；普通配置与 secret 分离。
- **用户价值**：用户可以真正调用自己的模型服务。
- **非目标**：不同时支持大量厂商；不捆绑本地大模型。
- **验收**：key 不进入导出配置/日志；health check、stream、cancel、timeout、错误码稳定。
- **建议验证**：mock HTTP + Windows secret-store 集成验证。

### RC04 — 真实选区解释链路

- **依赖**：RC01–RC03。
- **目标**：解释 / 为什么 / 举例 / 总结 / 翻译真正通过 `AiProvider` 工作。
- **验收**：请求前范围可见；回答带来源；取消立即停止；失败不改变用户内容。

### RC05 — 阅读伴侣侧栏：当前文档问答

- **目标**：围绕当前文档/选区连续提问；复用右侧上下文 contribution。
- **非目标**：不做全工作区检索，不做 Agent。
- **验收**：切换文档时上下文明确切换；历史不会误带到另一文档；来源可跳回。

### RC06 — “我刚刚读了什么？”

- **目标**：总结最近真实阅读片段，不总结整篇。
- **依赖**：RC01、RC04 或 RC05 的 provider 链路。
- **验收**：搜索跳转/目录跳转/切换文档场景不会把大片未读正文带入；结果 3–5 条且可展开来源。

### RC07 — 人物 / 术语记忆卡

- **目标**：从已读范围提取实体与短摘要，支持来源定位和手动清空。
- **非目标**：不做复杂图数据库。
- **验收**：重复实体可合并；派生数据删除后可重建；不会修改正文。

### RC08 — 防剧透阅读记忆地图

- **依赖**：RC07 + 可靠 `ReadCoverage`。
- **目标**：展示人物/概念/事件关系。
- **验收**：默认只使用已读证据；每条边可追溯来源；未读正文不发送给模型。

### RC09 — 工作区 RAG

- **目标**：在现有词法搜索上增加可选语义召回。
- **非目标**：不替换现有搜索，不默认远程 embedding。
- **验收**：结果带来源；embedding 可全部删除重建；关闭语义检索后原搜索无回归。

### RC10 — 写作辅助候选结果

- **目标**：改写/扩写/缩写/标题/frontmatter 建议。
- **验收**：所有修改先 diff，再由用户应用；取消和失败不写文件。

## 7. 推荐文件边界

实际文件名以届时架构为准，但职责建议保持：

- `src/app/ai/`：provider、request、consent、stream state；
- `src/app/reading-context/`：ReadingContextSnapshot / ReadCoverage；
- `src/components/`：选区动作和阅读伴侣 UI，只消费服务接口；
- `src/app/commands/`：AI 动作 command contribution；
- `src-tauri/`：secret storage / 必要网络能力边界，不把 provider 业务塞进大 command 文件；
- `.moyang/` 或 app cache：只保存可重建的阅读 AI 派生数据，格式必须版本化。

如果 v1.0 前的重构形成了不同目录，不要为了匹配本文强行搬文件；保持职责边界即可。

## 8. 测试基线

每个 AI UI 切片至少覆盖：

- 正常响应；
- streaming；
- cancel；
- timeout / provider error；
- 切换文档；
- 选区消失；
- 键盘/焦点；
- 深浅主题与 720/1240px 关键布局。

涉及上下文范围时额外覆盖：

- 长文档；
- 目录跳转；
- 文内搜索跳转；
- 返回历史；
- 当前文档切换；
- 未读区域不会被默认加入 spoiler-safe 请求。

涉及 secret / network 时额外覆盖：

- 导出设置不含 secret；
- 日志 redaction；
- 无 key / 错 key / endpoint unreachable；
- 取消后不继续处理迟到响应。

## 9. 成功标准

AI 阅读伴侣不是以“功能数量”判断成功。优先看：

- 用户能否在不离开阅读流的情况下获得解释；
- AI 是否总能说明自己看了什么；
- 是否能避免明显剧透；
- 关闭 AI 后应用是否仍然完整、轻量；
- 新功能是否通过 `AiProvider / ReadingContext / CommandService` 接入，而不是重新堆进 `App.tsx`；
- 每个垂直切片能否在约 0.5–3 天内独立开发、测试、回滚和交接。

## 10. 后续 AI 接手规则

1. 先读 `AGENTS.md`、`docs/AI-TASKS.md`、`docs/ROADMAP.md` 和本文。
2. v1.0 前不要因为本文存在而跳过当前稳定性/发布任务。
3. v1.0 完成后，从 RC01 开始，每次只把 1–2 个满足依赖的切片加入 `AI-TASKS.md`。
4. 开发前搜索 Issues / PR，已有同类任务就复用，不重复立项。
5. 一个切片、一个 `codex/` 分支、一个 PR；UI 变更补相关 E2E。
6. 任何超出当前切片的“顺手优化”只记录，不扩大 PR。
