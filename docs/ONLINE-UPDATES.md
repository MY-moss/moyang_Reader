# 在线更新与发布

## 用户操作

0.13 起使用独立签名发布通道，不连接旧项目的更新源。首次使用默认启动检查；已有设置中明确关闭的选项保留原值。在「设置 → 应用更新」可手动检查，也可开启「发现新版后自动下载」。

更新分两步：下载并校验签名，随后点击「保存并重启更新」。重启前完成文档保存、设置写入与 AI / 聊天暂存；遇到保存冲突或写入失败时保留当前窗口。下载不会自动结束你的工作。

便携更新只包含主程序、MCP 与使用文档，不重复下载本地模型。新版本放入独立目录，完成切换后保留上一版；个人文档、AI 数据库和聊天数据库保持原位置。正在使用旧 MCP 的客户端不会被强行结束；需要新版 MCP 时，在新应用的「接入与备份」重新安装连接，再重启客户端。

源码工作区使用 `release/latest.json` 定位当前版本，根目录启动方式不变。独立下载的 ZIP 解压后直接打开主程序；后续更新放在该目录的 `updates/` 下，原来的主程序会转到当前版本。

## 失败与回退

- 网络失败：当前版本继续使用，可以重新检查并下载。
- 签名无效：不解包、不安装，不提供绕过校验的按钮。
- 文件缺失或版本清单不匹配：不切换当前入口。
- 切换前等待旧进程结束；启动立即失败时，恢复 `previous.json` 指向的版本，并写入 `update-error.txt`。下一次启动显示更新未完成的提示。
- 手动回退：关闭阅读器，在当前 `release/` 或 `updates/` 目录将 `previous.json` 复制为 `latest.json`，重新打开原启动入口。不要移动个人数据库。

上一版用于回退，也可能被 MCP 客户端或嵌入模型服务使用。不要直接删除还在使用的程序目录，尤其是包含 `ollama` 的原始目录。更新版本会复用记录的本机运行程序路径；移动完整软件目录后，如果模型路径失效，可在「接入与备份」重新准备本地运行程序。

## 维护者发布流程

1. 完成源码、文档、浏览器和真实桌面检查，正常合并经过质量检查的 PR。
2. 执行 `npm run package`，生成本次成功构建的独立便携包。
3. 执行 `node scripts/prepare-online-update.mjs`。脚本核对包版本与可执行文件校验和，排除模型和本机更新元数据，生成 ZIP、签名、`reader-update.json` 与 SHA256 清单。
4. 创建 `reader-v<版本>` GitHub Release，上传这些发布文件，核对其下载与签名后再发布为最新版本。不要把模型、个人数据库、API 密钥或签名私钥上传到仓库或 Release。
5. 用发布应用检查实际通道；下一版本应演练真实升级与回退。首次正式通道发布只能验证当前版本检查和隔离升级场景，不能把尚不存在的未来升级称作已完成验收。

发布签名私钥默认位于本机 `.local/release-signing/moyang-update.key`，或通过 `TAURI_SIGNING_PRIVATE_KEY_PATH` 指定。应单独备份私钥；丢失后不能随意替换同一通道的验证公钥。源码只包含公钥。测试使用临时生成的另一把密钥，不读取真实发布私钥。

通道：[独立更新清单](https://github.com/MY-moss/moyang_Reader/releases/latest/download/reader-update.json)。自定义目标为 `windows-x86_64-portable`。复用 [Tauri updater 的签名下载](https://v2.tauri.app/plugin/updater/)，签名校验成功之后才解压；安装器由本项目便携目录切换流程接管。

## 自动化验收

原生测试覆盖有缺陷的包和版本不一致；桌面测试使用本机 HTTP 服务及临时密钥，验证正常签名、篡改、下载失败与下载后尚未切换。`scripts/test-update-activation.ps1` 在临时目录验证入口切换、启动失败回退和个人文件保留。正式版本不编译测试端点覆盖入口。
