# ADR-0009：批量 DOCX 采用增量 ZIP 归档

## 状态

已在 #87 的开发切片中实施；真实 Windows 桌面导出回归已由独立验收切片覆盖。

## 背景

前置的 #87 切片已经把 JSZip 的内部输出流分块写入同目录临时文件，但 DOCX 仍要先在内存中完成整卷 `document.xml`、图片集合和 JSZip 条目。Worker 能避免阻塞界面，却不能降低这份归档的驻留内存。批量导出需要继续保持可取消、失败可清理和目标文件不被半成品覆盖。

## 决策

- 仅替换批量 `streamDocxExport` 路径；单文档 `buildDocxExport` 继续使用成熟的 JSZip 生成路径。
- 用轻量 ZIP 写入器按条目输出：`document.xml` 在遍历每篇文档时按区块写入，XML 条目使用浏览器原生 raw DEFLATE，已经压缩的图片直接写入。
- 使用 ZIP 数据描述符记录流式条目的 CRC 和大小，所有条目完成后再写中央目录；图片关系、超链接关系和 `[Content_Types].xml` 在正文遍历完成后生成。
- 在 WebView2 不支持 raw DEFLATE 时，回退到原 JSZip 内部流；流已经开始写出后不尝试静默切换实现，交由现有临时文件清理边界处理。

## 不变的契约

- Markdown/HTML/Word 转换结果、分卷上限、输出文件名、保存路径授权和同目录隐藏临时文件不变。
- 取消或异常仍返回原有错误边界，不能提交半成品目标文件；调用方继续负责 `discardBinaryFile`。
- 图片关系、外部超链接、页眉页脚、页码、表格、列表和标题层级必须能被现有 DOCX/ZIP 测试读取。

## 取舍与风险

- 原生 `CompressionStream` 不保证所有旧 WebView 都支持，因此必须保留 JSZip 回退；回退会恢复旧的内存特征，但不影响正确性。
- 流式 ZIP 使用 ZIP32 头；现有分卷上限远低于 4 GiB，若未来扩大上限，必须先另行设计 ZIP64。
- 单个复杂 HTML 块仍由既有 `blockXml` 一次生成；若它成为新的实际峰值，应另开小切片实现递归区块写出，不在本 ADR 中扩大范围。
- 自定义 ZIP 写入器增加少量代码和维护成本，但不新增运行时依赖，也不会把 JSZip 从构建中移除。

## 验证

- 定向导出测试覆盖普通批量、图片/超链接、取消和 raw DEFLATE 不可用回退。
- 同一测试进程、同一合成数据分别测量旧 JSZip 与增量路径；当前本机样本（32 篇、约 16 MiB 高变化文本）堆峰值约从 82.8 MiB 降到 75.0 MiB。该结果只用于回归趋势，不能作为所有机器的性能承诺。
- 已完成格式检查、前端全量质量门禁和真实 Windows 桌面导出/取消清理回归；最新批量场景 smoke 通过 1/1，并记录了上下文面板交互、渲染事件循环、取消延迟和 Working Set 趋势。后续只需在更大真实图片、长单块内容和重复矩阵下补充证据，不改变本 ADR 的归档边界。

## 回滚

回滚 PR #332 的合并提交即可恢复原 JSZip 流式路径；桌面验收测试可独立回滚，不涉及用户文档迁移、数据库迁移或 Release 资产回滚。
