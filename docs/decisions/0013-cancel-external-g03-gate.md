# ADR 0013：取消外部 G03 治理门禁，保留仓库内控制面

## 状态

**已废止，仅保留为历史记录。**

本文曾部分替代 ADR 0011。2026-09-05 起，ADR 0011 所描述的 policy / plan / state / T0–T3 治理状态机整体停止使用，因此本文关于 G01/G02/G03、批准队列和取消项状态迁移的规则也不再约束当前开发。

ADR 0012 的“v1.0 前先建设内部能力接口，不提前开放第三方插件 SDK”仍然有效。

## 日期

2026-09-04（历史决策）

## 背景

ADR 0011 计划通过独立 GitHub App、Code Owner 规则和两个探针，在仓库外强制隔离 AI 身份。当前仓库只有所有者连接，无法在不新增账户权限和私钥管理的前提下完成该外部门禁。继续把 G03 留在批准队列会让实际开发长期停在人工配置点，也会诱使后续接手者把未完成的外部条件误读成产品开发阻塞。

## 历史决策

当时决定：

- 取消批准队列中的 G03；
- 暂时保留 G01/G02 的 policy、plan、state、本地校验和风险分级；
- 不声称已经拥有独立 AI App 或仓库外强制身份隔离；
- 继续对凭据、权限、数据迁移、发布等高风险项保留人工确认。

## 后续变化

实践证明，即使取消 G03，剩余状态机对个人开发项目仍然过重，并造成了正常 PR 因治理状态耦合而失败的情况。因此后续直接采用轻量 TODO 工作流，而不是继续修补旧状态机。

当前有效流程见：

- `AGENTS.md`
- `docs/AI-TASKS.md`
- `docs/AI-WORKFLOW.md`
- `docs/FUTURE-DEVELOPMENT-PLAN.md`

本文只用于解释旧提交与历史术语，不应作为恢复旧门禁的依据。
