# ADR 0013：取消外部 G03 治理门禁，保留仓库内控制面

## 状态

已接受，作为 v0.11 计划修订。

## 日期

2026-09-04

## 背景

ADR 0011 计划通过独立 GitHub App、Code Owner 规则和两个探针，在仓库外强制隔离 AI 身份。当前仓库只有所有者连接，无法在不新增账户权限和私钥管理的前提下完成该外部门禁。继续把 G03 留在批准队列会让实际开发长期停在人工配置点，也会诱使后续接手者把未完成的外部条件误读成产品开发阻塞。

## 决策

- 取消批准队列中的 G03；保留 G01/G02 已建立的 policy、plan、state、生成摘要和本地路径/状态校验。
- 在 `plan-v1.json` 中保留 G03 的历史任务定义，并通过 `cancelledTasks` 记录取消原因和时间；取消项不计入 `completedTaskIds`。
- M1101 直接依赖 G02。状态机只能跨过计划明确标记的取消项，不能跨过活动任务，也不能由 AI 自行新增或删除取消记录。
- 保留 T3、治理文件、凭据、权限、数据迁移、发布和安全边界的人工确认；取消 G03 不等于取消这些风险门禁。
- 不声称已经拥有独立 AI App 或仓库外强制身份隔离；未来若恢复外部门禁，必须新增并批准计划修订。

## 备选方案

### 保留 G03 并等待独立 App

安全边界最完整，但当前需要账户级注册、安装和私钥管理，开发队列无法在现有权限下继续推进，因此暂不采用。

### 删除 G01/G02 的仓库内控制面

可以回到旧的提示词和分散文档，但会丢失已经完成的上下文收敛、状态校验和越界修改门禁，因此拒绝。

## 后果

- M1101 及后续 T0–T2 可以在本地控制面和质量门禁通过后继续自动交付。
- 仓库不再具备由独立 GitHub 身份提供的强制隔离；管理员必须把这一限制视为已知风险，而不是将 GitHub 连接当作 AI Bot。
- 计划取消项仍可追溯，状态机不会把它伪装成已完成任务或允许任意跳队列。

## 关联

- 不改变 [ADR 0012](0012-internal-capability-ports-before-plugins.md) 的内部能力接口边界。
