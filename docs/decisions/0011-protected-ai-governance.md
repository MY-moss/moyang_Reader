# ADR 0011：采用受保护策略与可变运行状态分离的 AI 治理

## 状态

已接受；外部 GitHub App、Code Owner 探针和 G03 阻塞部分由 [ADR 0013](0013-cancel-external-g03-gate.md) 取代。

## 背景

原有 Markdown 交接把当前任务、权限、主线 SHA 和历史复制到多个文件。AI 可以同时修改任务说明和校验规则，既容易读取过期任务，也无法阻止它先放宽规则再继续交付。

## 决策

- 将权限策略和用户批准队列作为受 Code Owner 保护的治理层，将当前任务、验证和交付证据作为可由 AI 更新的运行层。
- 使用结构化 policy、plan、state 保存唯一事实；`NEXT.md` 只从它们生成。
- AI 只能沿批准队列前进一个任务。计划内 T0–T2 可以自动交付；T3、治理、发布、凭据、权限和数据迁移必须使用与任务摘要绑定、由 Code Owner 合入主线的审批凭证。
- 仓库外部强制保护使用独立 AI bot/App 身份和 Code Owner 审批。保护探针未通过前不启用自动合并。

> 上述最后一条外部强制保护决定已被 ADR 0013 取消；policy、plan、state 分层和高风险人工确认仍然有效。

## 备选方案

### 继续使用 Markdown 和提示词

实现简单，但只能约束合作良好的模型，不能可靠校验状态迁移、自我授权和重复事实，因此不采用。

### 所有 AI 改动都人工审查

安全边界清楚，但无法满足 T0–T2 连续自动交付的目标，因此只对治理和 T3 保留人工检查点。

## 后果

- 默认接手只需稳定规则和当前紧凑状态，减少过期上下文和 Token。
- 治理层修改会刻意变慢；这是防止 AI 自我放权的必要成本。
- 如果 AI 与仓库所有者共用管理身份，只能防止意外偏航，不能构成强制权限隔离。
