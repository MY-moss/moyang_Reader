# ADR 0011：采用受保护策略与可变运行状态分离的 AI 治理

## 状态

**已废止，仅保留为历史记录。**

2026-09-05 起，仓库改用 `AGENTS.md + docs/AI-TASKS.md + GitHub Issues/PR + Quality checks` 的轻量个人维护流程。本文描述的 policy / plan / state、T0–T3、审批凭证、Code Owner AI 门禁和生成式 `NEXT.md` 均不再约束当前开发，也不得由后续 AI 根据本文重新启用。

关于产品内部扩展与 AI provider 的长期边界，ADR 0012 仍然有效。

## 背景

原有 Markdown 交接把当前任务、权限、主线 SHA 和历史复制到多个文件。AI 可以同时修改任务说明和校验规则，既容易读取过期任务，也无法阻止它先放宽规则再继续交付。

## 历史决策

当时决定：

- 将权限策略和用户批准队列作为受 Code Owner 保护的治理层，将当前任务、验证和交付证据作为可由 AI 更新的运行层。
- 使用结构化 policy、plan、state 保存唯一事实；`NEXT.md` 只从它们生成。
- AI 只能沿批准队列前进一个任务；高风险任务使用审批凭证。
- 曾计划通过独立 AI bot/App 身份和 Code Owner 审批提供仓库外强制保护，后由 ADR 0013 取消该部分。

## 为什么废止

对当前单人维护项目而言，这套设计带来的审批、状态同步、上下文读取和 CI 成本明显高于实际收益，并已经产生阻塞正常开发和浪费 Token 的问题。

当前流程改为：

- 一个任务 / 一个分支 / 一个 PR；
- 后续 AI 从 `docs/AI-TASKS.md` 选择第一个合适的 TODO；
- 开工前检查当前代码、Issue 和 PR；
- 普通代码/UI/测试/文档按范围运行最小充分测试；
- 只对用户文件安全、密钥/证书、正式 Release/Tag 和无法伪造的外部验证保持真实风险边界；
- GitHub `Quality checks` 继续作为主线质量门禁。

## 历史价值

本文继续保留，用于说明为什么仓库曾出现 policy/plan/state/T0–T3 等术语，以及为什么后续选择删除它们。它不是当前开发说明。
