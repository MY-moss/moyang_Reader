# 产品方向与开发收敛审计 — 2026-09-17

## 结论

当前 `main` 没有发生严重产品跑偏，但已经进入必须收敛的阶段。

Moyang Reader 的实际产品形态已经从“轻量 Markdown 阅读器”扩展为“轻量、本地优先的 Windows 文档阅读工作台”。这与现有路线图方向基本一致，但已有能力和工程复杂度已经明显高于早期定位。如果继续在当前阶段叠加 Reading Inbox、AI、RAG、RSS、插件、知识库等新能力，高耦合中心和发布风险会迅速放大。

因此当前判断是：

- 产品主方向正确；
- 最近的模块化与 UX 收口工作方向正确；
- 功能扩展速度必须暂时降低；
- 发布、真实 Windows 验证与职责拆分需要优先于新功能；
- 历史上曾出现 AI governance 过度设计，但当前轻量任务队列已经是正确纠偏方向。

## 主要证据

### 1. 产品定位已经从单纯 Markdown 阅读器扩展

当前路线把 v1.0 定义为可靠、离线、本地优先的 Windows x64 阅读工作台，覆盖文件安全、阅读、编辑、搜索、关联、导出、恢复和更新。

这意味着后续对外描述、路线和实现都应围绕“轻量本地阅读工作台”统一，而不是继续以“纯 Markdown 查看器”的狭窄假设指导架构。

### 2. 当前最大结构风险仍是大型编排中心

`App.tsx` 虽然已经完成设置控制器和文档会话控制器等拆分，但仍承担大量 UI 编排、文件、工作区、搜索、导出、恢复和状态协调职责。

继续拆分是必要的，但目标不能是机械降低行数，而应是：

- 修改某个能力时只需要理解较小职责边界；
- 文件安全、工作区、命令、搜索、导出等领域有清楚输入/输出；
- 新功能不再默认接入 `App.tsx`；
- 每个拆分切片都可以独立测试和回滚。

Rust `commands.rs`、`styles.css`、`export.ts` 等大型文件遵循相同原则。

### 3. 最近开发主线已经开始正确收敛

近期已完成的主要工作包括：

- TS ↔ Tauri 命令契约集中化；
- 首批 IPC 运行时返回校验；
- 设置控制器提取；
- 文档会话生命周期提取；
- Rust document commands 第一阶段拆分；
- 快速打开 / 文内查找 / 阅读库搜索语义统一。

这些工作优先降低耦合和改善真实用户路径，没有继续横向制造新的产品模块，应继续保持这一节奏。

### 4. 历史 AI governance 曾出现过度设计，当前方案已经纠正

仓库曾短暂引入复杂 policy/state machine、额外状态控制、身份隔离和治理机制。随后已经主动移除大部分复杂流程，回到 `AGENTS.md + AI-TASKS.md + ROADMAP.md + 架构契约` 的轻量控制面。

后续不得因为历史文档、旧提交或旧 CHANGELOG 中仍出现 governance/state machine 描述，就恢复已经废弃的流程。

### 5. 发布出口目前落后于 main 的开发跨度

当前稳定 Release 与 `main` 之间已经积累多批结构、测试和 UI 改动。与此同时，Windows x64 PDF 落盘、旧版本自动升级、安装包签名和真实发布链路仍存在需要实机闭环的外部条件项。

因此在继续增加大型功能前，需要先把当前能力重新压成一个可以真实安装、升级、回归和发布的稳定版本。

## 当前决策

### v0.11 收敛顺序

默认按以下顺序继续：

```text
A07 命令面板
→ A08 右侧上下文面板键盘/ARIA
→ A09 顶栏信息架构与 Windows DPI
→ A10 CSS / 主题 / 小型视觉回归
→ 下一轮职责级 App / Workspace 拆分
→ v0.11 RC
→ Windows 实机完整回归与发布链路验证
→ v0.11 正式版
```

### v0.12 只做稳定性与真实边界

重点保持为：

- 5k / 20k 工作区 benchmark；
- 1MB / 10MB 大文件边界；
- 降级策略；
- 当前 main 主流程 UX 回归；
- Tauri 权限与负向安全测试；
- 不含正文和密钥的诊断摘要。

### 暂时冻结的能力

在 v0.11/v0.12 的前置条件满足前，不直接实现：

- Reading Inbox；
- Daily Note；
- Properties 表格视图；
- AI provider；
- RAG / embeddings；
- RSS / 自动远程内容抓取；
- 插件市场 / 任意第三方代码；
- 新账号、云同步或后台服务。

这些能力可以继续保留 Issue、ADR 和长期设计，但默认只分析，不创建实现 PR。

## 产品边界

Moyang Reader 后续继续坚持：

1. **轻量**：已有能力先做快、稳、好找，不以功能数量衡量进度。
2. **本地真源**：用户普通文件继续是真源，不依赖私有数据库才能读取。
3. **默认离线**：联网能力必须可选、可关闭，不成为核心依赖。
4. **文件安全优先**：写回、覆盖、恢复、外部修改、升级都必须可解释、可回滚。
5. **扩展受控**：未来 AI/插件只能经过能力端口和权限边界进入核心。
6. **发布事实优先**：CI 绿灯不能替代真实 Windows 安装、升级、签名和桌面路径验证。

## 后续复查触发条件

满足以下条件后，再复查是否解除功能冻结：

- A07–A10 完成；
- 下一轮主要职责拆分完成且没有新的高耦合中心；
- v0.11 RC 完成真实 Windows 主流程回归；
- 安装/升级/PDF/更新器链路有可验证结果；
- v0.12 性能与大文件边界已有测量数据；
- 无未处理的高严重度文件安全问题。

达到这些条件后，再决定 v0.13、Reading Inbox 或 AI 接缝哪个具有最高真实用户价值，而不是按照“哪个功能更酷”排序。
