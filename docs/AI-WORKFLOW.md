# Moyang Reader AI 开发工作流

本文件是所有 AI 接手本项目时的流程入口。它约束任务边界、上下文大小、验证方式、分支协作、发布节奏和交接格式。产品范围以 `docs/REQUIREMENTS.md` 为准，版本与安装包以 `docs/RELEASE-POLICY.md` 为准，当前状态以 `docs/AI-HANDOFF.md` 为准。

当前产品只维护 Windows x64 桌面版。浏览器版只用于本地预览和 Playwright 测试；不因一个功能临时增加 macOS、Linux、Windows ARM、移动端或云同步工作。

## 给任何 AI 的快速启动指令

```text
你正在维护 Moyang Reader。先执行 INTAKE 和 READY，不要直接编码。
只读取 docs/AI-WORKFLOW.md、docs/AI-HANDOFF.md 的当前状态/唯一下一步，以及与任务直接相关的规则、源码、测试和一个相似实现；上下文控制在 2000 行以内。
没有 Ready 任务就停止并列出候选，不自行扩展需求。一个任务只做一个垂直切片、一个主要分支、一个 PR；完成 VERIFY、CHECKPOINT、HANDOFF 后停止，不自动开启下一批。
不要粘贴完整源码、完整 CI 日志或完整工具输出；只报告路径、行号、根因、结论和下一步。
```

## 不可违反的效率规则

- 每个任务只读取一次相关技能和项目规则；重复使用时引用前次摘要，不重新读取全文。
- 上下文目标不超过 2000 行，优先使用 `rg`、摘要、文件路径和行号；禁止无必要地读取大型文件、完整日志或完整 CI 输出。
- 工具输出默认限制在约 4 KB；失败只保留首个根因和最小关键上下文。原始日志留在本机或 CI，不复制进对话。
- 同一命令最多自动重试一次；同一类型连续失败三次就停止，报告阻塞、已排查范围和需要的外部决策。
- 不重复查询没有变化的 Issue、PR、提交或 CI。每次 CI 查询必须记录提交 SHA、`run_id`、结论和最后变化时间。
- 不使用冗长的 `gh run watch` 或循环 `Start-Sleep` 作为默认等待方式。采用一次初查、一次有界等待、状态变化后再查；没有变化就停止轮询。
- 普通逻辑改动只运行针对性测试；UI 改动运行针对性测试加一个 E2E；发布、更新器、签名、安全、数据迁移或跨平台改动才运行完整质量门禁。
- 每个功能切片最多一次完整构建。开发阶段不反复生成稳定安装包；只有稳定批次才进入 Release 流程。
- 一个功能切片只有一个主要分支和一个 PR。分支合并后，从最新 `main` 创建新分支，不让旧 PR 长期承载多个主题。
- 用户说“继续开发”时，只从已经 Ready 的 backlog 选择最高优先级事项；没有 Ready 事项时先输出候选和选择理由，不自行扩展。
- 每次最多提出三个真正阻塞决策；已经确定的问题不重复询问。
- 功能切片完成并交接后停止当前任务，不自动开始下一批。

## 阶段门禁

每个切片必须按以下顺序推进。任何阶段不满足退出条件，都不能进入下一阶段。

### INTAKE：确认问题和值得做的原因

只做一次 Issue/反馈检查，记录：用户问题、用户价值、关联 Issue/PR、是否重复、优先级和非目标。Issue 查询只服务当前切片，不把所有历史 Issue 反复拉入上下文。

如果问题没有明确用户价值、与现有 Issue 重复且没有新证据，或属于 Won't 范围，直接停止并说明原因。

### READY：把任务钉死

开始编码前必须写出一页以内的任务上下文，至少包含：目标、非目标、验收标准、预计修改文件、依赖、风险、回滚方式、测试级别、版本分类和是否发布。缺一项就不是 Ready。

READY 还必须确认：工作区状态、当前分支、基于哪个 `main` 提交、Issue 状态和已有类似实现。未确认远程状态时，不假设“可以合并”。

### DISCOVERY：最小必要读取

读取顺序：

1. 本文件和 `docs/AI-HANDOFF.md` 的当前状态/唯一下一步；
2. 本任务直接相关的技能和项目规则，各一次；
3. 用 `rg` 定位相关符号；
4. 只读相关源码、相关测试和一个相似实现；
5. 记录不超过一页的事实摘要、文件行号和未知项。

不要通读仓库，不要为“以后可能用到”提前读取文件。发现任务实际超出范围时，回到 READY 重新切片，而不是继续扩大上下文。

### DESIGN：一页方案

方案只写现状、最小变更、状态/数据边界、异常路径、测试策略和回滚方式，最多一页。没有新证据时不进行无限讨论；高风险决策才增加 ADR。

### IMPLEMENT：一个垂直切片

只实现一个用户可感知的完整路径，同时更新必要的测试、文案和工程文档。禁止顺手清理无关代码、改 UI 主题、升级依赖或添加下一版本功能。遇到范围外问题记录 Issue/后续候选，不在当前分支处理。

### VERIFY：按风险分层

| 级别 | 适用范围                                         | 最小验证                                                                  |
| ---- | ------------------------------------------------ | ------------------------------------------------------------------------- |
| T0   | 纯文档、模板、统计脚本                           | 目标文件格式检查、脚本最小运行/帮助输出、`git diff --check`               |
| T1   | 普通逻辑、解析、索引、状态                       | 相关单测/集成测试、相关 lint/format；不默认全量构建                       |
| T2   | UI、交互、快捷键、布局                           | T1 + 一个相关浏览器 E2E；涉及真实桌面路径时增加一个 Windows desktop smoke |
| T3   | 更新器、签名、发布、保存安全、原生 IPC、数据迁移 | 完整质量门禁、一次完整构建、真实 Windows 验证和发布检查                   |

测试命令只覆盖变更风险。完整门禁使用仓库已有脚本：`npm run lint`、`npm run format:check`、`npm test -- --run`、`npm run build`、`npm run test:e2e`、`npm run test:e2e:desktop`、Rust test/fmt/clippy、`npm run release:check` 和 `npm run test:release`；不要因为习惯在 T0/T1 重复执行全部命令。

### CHECKPOINT：形成一个可审查交付物

验证通过后：

1. 检查 `git diff`、敏感文件和修改文件数量；
2. 创建一个目的清晰的提交；
3. 推送当前功能分支；
4. 创建一个对应 PR，填写本仓库 PR 模板；
5. 记录提交 SHA、PR、CI `run_id`、结论和最后变化时间。

功能分支与最新 `main` 无真实冲突且 Quality checks 全绿时，可以直接合并；只有真实冲突、检查失败、权限/安全/更新器/发布工作流/数据迁移风险才暂停。禁止强制推送覆盖他人提交。合并完成后立即停止，不在同一任务开启下一个切片。

### RELEASE：稳定批次才发布

纯文档、测试、模板、CI 或内部工具改动不创建安装包。用户可见功能达到稳定版本验收，或重要 Bug/保存/更新/签名/安全修复需要用户升级时，才按 `docs/RELEASE-POLICY.md` 创建 Windows x64 安装包、Release、`.sig`、`latest.json` 和 Cloudflare 镜像，并做在线资源与旧版本更新验证。

开发阶段不得为了“看看效果”反复生成稳定安装包。PR 中必须明确“无 Release / minor / patch”、目标版本和理由；没有发布就明确记录，不把未发布误报成已交付。

### HANDOFF：短交接后停止

交接只保留下一位 AI 真正需要的信息：当前分支和 SHA、完成内容、修改文件、验证结果、已知限制/风险、回滚方式、Issue/PR/Release 状态、唯一下一步、效率指标。不要把完整历史或完整日志复制进 `docs/AI-HANDOFF.md`。

## CI、失败和状态查询协议

CI 状态使用以下单行记录，不重复贴日志：

```text
sha=<commit> workflow=<workflow> run_id=<id> conclusion=<queued|in_progress|success|failure|cancelled> last_changed_at=<UTC> next_action=<poll once|stop|fix root cause>
```

失败处理顺序：

1. 只读取失败 job 的首个根因、相关文件和最近一段上下文；
2. 判断代码失败、环境失败、权限失败还是网络失败；
3. 同一命令最多重试一次；同类累计三次停止；
4. 如果是代码根因，补复现测试后修复；如果是外部阻塞，保留证据并报告，不换十个渠道重复尝试；
5. 任何重试、返工、取消或重新生成安装包都写入交接指标。

## 指标采集与改进判定

对原始 Codex JSONL 只做流式、结构化统计，不把原始日志提交到仓库。辅助脚本：

```powershell
node scripts/ai-workflow-metrics.mjs --file <session.jsonl> --cutoff-ordinal <任务开始前的最后 ordinal>
```

脚本统计模型请求、输入/缓存输入/输出 Token、阶段 Token、工具调用、重复输入、文件读取、CI 查询、构建/测试标记和失败标记。命令标记是上界估计，不等同于成功执行次数；CI 状态以实际 `sha/run_id/conclusion/last_changed_at` 记录为准。每个切片另外手工记录修改文件数、真实构建/测试次数、返工次数和耗时。

Token 统计使用每次 `token_count` 的 `last_token_usage` 累加。缓存输入不能直接等同于账单金额，但仍会占用上下文容量、增加请求处理延迟并影响用量上限；因此必须控制上下文和重复请求，而不是只看现金成本。

| 模型请求样本                       |                                  11,285 |
| 输入 / 缓存输入 Token              | 1,584,017,567 / 1,558,362,112（98.38%） |
| 总 Token（按每次 last usage 累加） |                           1,590,164,163 |

| CI 查询（按工具名） / 明确等待标记 |           736 / 291（文本标记上界 941） |
| 不同文件路径 / `App.tsx` 读取      |                                161 / 91 |
| 完全重复工具输入                   |                              至少 1,868 |
| 非零退出 / 工具错误 / 中止 turn    |                            352 / 50 / 1 |

连续三个切片后用中位数复盘是否改善：重复工具输入低于 5%；同一 CI run 通常不超过初查 + 两次有界查询；每切片完整构建不超过 1 次；同类失败不超过 2 次后停止；无范围外文件；交接完成率 100%。如果没有改善，先修流程，不直接加大模型或增加工具。
